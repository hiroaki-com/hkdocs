# 用語集（学習用）

このリポジトリで実際に使われている技術用語を、英語学習を兼ねて解説する文書です。

正（ソース・オブ・トゥルース）は各設計文書とコードであり、この文書は契約でも仕様でもありません。
仕様が変わってもこの文書が変わらないのが正常です。値・鍵・件数・パス等は意図的に書きません。

読み方:

- 見出し行が、他の現場でもそのまま通じる一般的な定義です。
- 直訳 = 技術用語である前の、素の英単語としての意味。
- 本レポ = このリポジトリでの具体的な指示対象。
- 背景 = なぜその設計か、間違えやすい点、隣接概念との違い。

## 1. サイト生成の基盤

### Static Site Generator (SSG) — ビルド時にHTMLを生成しきり、配信時はファイルを返すだけの仕組み

 - 直訳　 : 静的な（動かない）サイトの、生成器
 - 本レポ : Docusaurus がビルドで全ページのHTMLを吐き、コンテナはそれをそのまま配るだけ。リクエストごとのサーバ処理は無い
 - 背景　 : 「静的」はサーバが動的処理をしない意味であって、ページが動かない意味ではない。閲覧時にJavaScriptが動くのは別の話。DBもアプリサーバも要らないため、後述の Cloud Run 上でも極めて安く速い

### Docusaurus — ドキュメントサイト向けの静的サイト生成フレームワーク

 - 本レポ : このサイト全体の土台。ルーティング、サイドバー、テーマ、i18n、検索連携までを引き受ける
 - 背景　 : React を土台にしつつ「ドキュメント」という用途に振り切っているのが特徴。汎用のReactフレームワークと違い、規約に従う限り設定がほぼ不要になる（語源はギリシャ語 δοκός（梁）+ σαῦρος（トカゲ）の造語で、恐竜のドキュメント関連の語呂合わせ）

### Preset — 複数のプラグインとテーマをひとまとめにした既定セット

 - 直訳　 : あらかじめ（pre）設定された（set）もの
 - 本レポ : classic preset を読み込むことで、docs・blog・テーマ・サイトマップ・アクセス解析の設定を一箇所にまとめている
 - 背景　 : プリセットは「便利な束」でしかなく、個別プラグインを直接足すこともできる。実際このリポジトリでは、日記を別ブログとして扱うためにブログ用プラグインをプリセットとは別にもう一つ追加している

### Plugin — フレームワークの拡張点に差し込む追加機能の単位

 - 直訳　 : 差し込む（plug）もの（-in）。電源プラグの比喩
 - 本レポ : 日記をブログとは別系統のコンテンツとして生やすために、ブログ用プラグインを二重に登録している
 - 背景　 : 同じプラグインを複数回使うときは識別子を分ける必要がある。これは「同じ部品を2つ挿すならラベルを貼れ」という一般則で、Docusaurus 特有の話ではない

### Theme — 見た目とページ骨格を提供するコンポーネント群

 - 本レポ : クラシックテーマに加え、図を描くためのテーマを追加している。配色やレイアウトの上書きは独自CSSで行う
 - 背景　 : テーマは「配色」ではなく「UIコンポーネントの実装一式」を指す。テーマが持つコンポーネントを自前実装に差し替える操作を swizzle と呼ぶ

### Swizzle — テーマ内部のコンポーネントを取り出して自前で上書きすること

 - 直訳　 : かき混ぜる、混ぜ合わせる（もとはカクテルを撹拌する語）
 - 本レポ : 実行用のコマンドが用意されているのみで、現状は使わずCSSと独自コンポーネントで足りている
 - 背景　 : 便利だが、テーマ更新時に自前コピーが取り残されて壊れる。使わずに済むならその方が保守は軽い

### Markdown — 記号で構造を示す軽量記法

 - 直訳　 : markup（組版指定）をもじって「下げる（down）」＝軽くした、の意
 - 本レポ : 記事・ドキュメント・日記の本文形式
 - 背景　 : HTML の対義的な洒落で名付けられており、「マークダウンする（値下げする）」の意味とは無関係

### MDX — Markdown 中に JSX（React の構文）を書ける拡張形式

 - 本レポ : 共有ボタン等のReactコンポーネントを本文へ埋め込むために使う。純粋な文章のみのファイルは通常のMarkdownのまま
 - 背景　 : MDX は HTML コメントを解釈しないため、記事内のコメントや抜粋境界のマーカーは JSX 式のコメント形式で書く必要がある。ここは実際に本番ビルドを落としやすい罠

### Frontmatter — ファイル先頭に置くメタデータ領域

 - 直訳　 : 本の「前付け」。扉・目次など本文前のページ群を指す製本用語
 - 本レポ : 記事のタイトル、著者、タグ、説明文などをYAMLで記述する領域
 - 背景　 : 本文ではなくビルドへの指示。ここの説明文が検索結果やSNSカードの文面になるため、体裁ではなく実効がある

### Remark / Rehype — Markdown と HTML をそれぞれ木構造として変換するプラグイン基盤

 - 本レポ : 数式記法を解釈する側と、それを数式として描画する側の二段構えで組み込んでいる
 - 背景　 : remark は Markdown の構文木、rehype は HTML の構文木を扱う。数式が「書けるが表示されない」ときは、たいてい二段のうち片方しか入っていない

### Mermaid — テキスト記述から図を生成する記法

 - 本レポ : 構成図をコードブロックとして書き、ビルド時に図として描画する
 - 背景　 : 図を画像ではなくテキストで持てるため、差分が読めてレビューできる。画像バイナリを避けたい文書リポジトリと相性が良い

## 2. コンテンツと国際化

### i18n — 多言語対応の仕組み全般

 - 直訳　 : internationalization の頭と尾の間に18文字あることによる略記（数字略語、numeronym）
 - 本レポ : 日本語を既定ロケールとし、英語を追加ロケールとして持つ。翻訳文はロケール別のディレクトリに分離する
 - 背景　 : l10n（localization）と対で使われる。i18n が「多言語を扱える構造にすること」、l10n が「特定の言語・地域に合わせること」

### Locale — 言語と地域の組み合わせを表す識別子

 - 直訳　 : 場所、現場（フランス語由来の名詞）
 - 本レポ : 日本語と英語の2つ。ビルドはロケールごとに実行され、英語版はURLに接頭辞が付く
 - 背景　 : ロケール別ビルドでは、サイトの基準URLに既にロケール接頭辞が含まれている。ここを知らずに絶対URLを組み立てると接頭辞が二重に付く

### Translation string / Translate API — UI文言を翻訳可能な単位として登録する仕組み

 - 本レポ : コンポーネント内の固定文言は、識別子と既定メッセージの組で登録し、翻訳ファイル側に対訳を持つ
 - 背景　 : 「文言を直書きしない」のが要点。記事本文（コンテンツ）はファイルごと翻訳し、UI文言（ラベル）は文字列単位で翻訳する、と対象で使い分ける

### Truncate marker — 一覧に出す抜粋の終端を示す印

 - 直訳　 : truncate は「先端を切り落とす」。角を落とした立体を truncated と呼ぶのと同じ語
 - 本レポ : 記事本文の途中に置き、一覧ページではそこまでを抜粋として表示させる
 - 背景　 : 置き忘れると一覧に全文が流れ込む。設定次第でビルド時に警告される

### Slug — URLに使う、短く安全な識別文字列

 - 直訳　 : ナメクジ。転じて印刷業界で「鉛の小塊」「記事の仮見出し」を指した語
 - 本レポ : 記事ファイル名の日付以降の部分がURLの末尾になる。frontmatter で明示した場合はそちらが優先される
 - 背景　 : 語源は活版印刷の現場語で、原稿を識別するための短い符牒。技術用語というより現場の符牒がそのまま残った例

### CMS — 非エンジニアでもコンテンツを更新できる管理画面

 - 直訳　 : Content Management System、内容を管理する仕組み
 - 本レポ : 日記の投稿・編集をブラウザ上のフォームから行い、その結果がリポジトリへのコミットになる
 - 背景　 : いわゆる Git-based CMS。DBを持たず、保存＝コミットである点が従来型CMSとの決定的な違い。原稿の履歴がそのままGit履歴になる

### Git Gateway / Identity — ブラウザ上の管理画面から、認証を通してGitリポジトリへ書き込ませる中継役

 - 直訳　 : gateway は「門」「関所」。通す/通さないを判断する境界
 - 本レポ : 管理画面が直接GitHubに書くのではなく、認証サービスを経由してコミットが行われる構成
 - 背景　 : 閲覧者にリポジトリの書き込み権限を配らずに編集させるための中継。認証まわりの通信先は、後述のCSPで明示的に許可しないと遮断される

## 3. ビルドと依存管理

### Package manager — 依存ライブラリの取得と配置を担うツール

 - 本レポ : pnpm を使い、バージョンは package.json のフィールドで固定している
 - 背景　 : npm / yarn / pnpm は互換のようで挙動が違う。混ぜるとロックファイルが二重になり、再現性が壊れる

### pnpm — ハードリンクで実体を共有する、省スペース志向のパッケージマネージャ

 - 直訳　 : performant npm（高性能なnpm）の略。performant は「性能が出る」の意の形容詞
 - 本レポ : 依存の導入、ビルド、型検査など、すべてのスクリプト実行の入口
 - 背景　 : 依存ツリーを平坦化しないため、「宣言していないパッケージがたまたま使えてしまう」事故が起きない。厳格さが利点でもあり、他ツール前提の手順書がそのままでは動かない原因でもある

### Lockfile — 依存の解決結果を固定して記録するファイル

 - 直訳　 : 錠をかける（lock）ファイル
 - 本レポ : ビルド環境ではロックファイルどおりの導入を強制し、ズレていれば失敗させる
 - 背景　 : package.json は「許容範囲」、ロックファイルは「実際に入れた版」。前者だけでは同じ環境が再現できない

### Frozen lockfile — ロックファイルを一切書き換えずに導入させるモード

 - 直訳　 : frozen は freeze の過去分詞で「凍結された」
 - 本レポ : イメージのビルド時に指定し、CI上で依存が勝手に更新されるのを防ぐ
 - 背景　 : ローカルでの導入と違い、CIでは「解決し直す」こと自体が事故。差分があれば直すのは人間の仕事だ、という思想

### Corepack — Node.js に同梱された、パッケージマネージャのバージョン切替機構

 - 直訳　 : core（中核）+ pack（package の略）。Node本体側に取り込まれた梱包係
 - 本レポ : ビルド用イメージ内で有効化し、package.json に書かれた版のpnpmを使わせる
 - 背景　 : 「手元とCIでpnpmの版が違う」を構造的に潰すための仕掛け。ただし実行時に外部レジストリからの取得が走り得るため、本番の起動コマンドでは経由させない方が堅い

### Type checking — 実行せずに型の整合を検査すること

 - 本レポ : TypeScript のコンパイラで型のみを検査する。出力物は作らず、検証専用に走らせる
 - 背景　 : ここにはテストスクリプトが無く、型検査とビルド成功が事実上の防波堤になっている

### Hot reload — 保存と同時に画面へ変更が反映される開発時の挙動

 - 直訳　 : hot は「稼働したまま」。止めずに（hot）積み直す（reload）
 - 本レポ : 開発用コンテナで有効。ファイル監視が不安定な環境向けに、ポーリングへ切り替える設定が用意されている
 - 背景　 : コンテナ越しのファイル共有では、OSのファイル変更通知がゲストへ届かないことがある。そのときだけ、総当りで見張るポーリングに落とす

## 4. コンテナと配信

### Container — アプリと依存をまとめ、隔離して動かす実行単位

 - 直訳　 : 貨物コンテナ。中身が何でも同じ規格で運べることの比喩
 - 本レポ : ビルド済みサイトと最小限の実行環境を1イメージに固め、そのままクラウド上で動かす
 - 背景　 : 仮想マシンと違いOSカーネルは共有する。「軽い仮想マシン」ではなく「隔離されたプロセス」と捉えた方が挙動を誤らない

### Image — 停止した設計図としてのコンテナ（実体との対）

 - 本レポ : ビルドでイメージを作り、レジストリへ送り、実行環境がそれを起動する
 - 背景　 : イメージはクラスや実行ファイル、コンテナはインスタンスやプロセスに相当する。「イメージを再起動する」という言い方は成立しない

### Multi-stage build — ビルド用と実行用の段を分け、成果物だけを持ち越す手法

 - 直訳　 : 複数の（multi）段階（stage）に分けた組み立て
 - 本レポ : 前段で依存導入とサイト生成を行い、後段には生成物と実行に必要な最小限だけを複製する
 - 背景　 : 目的はイメージの縮小だけでなく攻撃面の縮小。コンパイラやビルド時の秘密情報を最終イメージに残さないことに意味がある

### Layer cache — 変更が無い工程の結果を再利用する仕組み

 - 本レポ : 依存定義ファイルだけを先に複製してから依存を導入し、そのあとでソース全体を複製する
 - 背景　 : 上の行が変わると以下は全部やり直しになる。だから「変わりにくいもの＝依存」を先に、「変わりやすいもの＝ソース」を後に置く。この順序に意味があることが、初見では最も分かりにくい

### Non-root user — 管理者権限を持たない利用者としてプロセスを動かすこと

 - 本レポ : 最終イメージでは非特権ユーザに切り替えてから起動する
 - 背景　 : コンテナの既定は root。破られたときの被害範囲を、あらかじめ狭めておくという発想（最小権限の原則）

### Serverless / Cloud Run — サーバ管理をせず、コンテナを必要なだけ起動させる実行基盤

 - 直訳　 : serverless は「サーバが無い」ではなく「サーバを意識しなくてよい」の意
 - 本レポ : ビルド済みコンテナをここで動かし、公開URLで配信している
 - 背景　 : 需要が無ければゼロまで縮む代わり、久々のアクセスでは起動待ちが生じる（コールドスタート）。起動時に外部から何かを取りに行く設計は、この待ち時間を悪化させる

### Registry — コンテナイメージを保管し、配布する保管庫

 - 直訳　 : 登録簿。登記所の registry と同じ語
 - 本レポ : ビルドしたイメージへタグを付け、ここへ送ってから実行環境へ配る
 - 背景　 : Git のリモートリポジトリに相当する立ち位置。デプロイとは実質「レジストリのどの版を指すか」の切り替えである

### Image tag — イメージの版を指す名札

 - 本レポ : コミットのハッシュをタグに使い、どのソースから作られたイメージかを一意に辿れるようにしている
 - 背景　 : latest のような可変タグは上書きされるため、後から「本番で動いていた実体」を再現できない。不変なタグを使うことが追跡可能性の前提

### Cross-platform build — 実行先とは異なるCPUアーキテクチャ向けにビルドすること

 - 本レポ : ARM系の手元マシンから、x86_64向けのイメージを明示的に指定してビルドする
 - 背景　 : 指定を忘れると、手元では動くのにクラウド上で「exec format error」で落ちる。手元と本番でCPUが違う時代特有の落とし穴

### Port — 通信の宛先を分ける番号

 - 直訳　 : 港。船（通信）が接岸する場所の比喩
 - 本レポ : 開発用は開発サーバの待受ポート、本番用イメージは配信用ポートを公開する
 - 背景　 : コンテナ内部の待受と、外へ公開する割り当ては別物。開発時に外部公開範囲を絞るのは、待受側ではなくホスト側の割り当てで行う

### SPA fallback — 未知のパスへのリクエストを単一のHTMLへ寄せる配信設定

 - 直訳　 : fallback は「後退して受け止めるもの」。予備の受け皿
 - 本レポ : 静的ファイル配信サーバをこのモードで起動している
 - 背景　 : クライアント側ルーティングを持つサイトで、直接URLを叩かれた際の404を避けるための定番設定

## 5. CI/CD と自動化

### CI / CD — 変更を頻繁に統合して検証し、そのまま届けるまでを自動化する慣行

 - 直訳　 : Continuous Integration（継続的統合）/ Continuous Delivery（継続的な提供）
 - 本レポ : 変更に対してビルドが通ることを検証し、公開対象のブランチではイメージ生成からデプロイまでを自動実行する
 - 背景　 : CI は「壊れていないことの確認」、CD は「届けること」。同じ流れに見えて目的が違うので、失敗したときの対処も違う

### Workflow / Job / Step — 自動化処理の入れ子構造の単位

 - 本レポ : ビルド検証、デプロイ、SNS投稿がそれぞれ別のワークフローとして定義されている
 - 背景　 : ワークフローが台本、ジョブが場面、ステップが台詞。ジョブ単位で実行環境が分かれるため、ジョブをまたぐとファイルは引き継がれない

### Trigger — 自動処理を起動させる出来事

 - 直訳　 : 銃の引き金
 - 本レポ : 対象ブランチへの反映や、手動実行が起点になる
 - 背景　 : 「いつ動くか」を読み違えると、意図しないタイミングで本番に出る。自動化の事故はロジックよりトリガー設定に集中する

### Concurrency control — 同じ処理が同時に走らないよう直列化する制御

 - 直訳　 : concurrency は「同時に起きること」
 - 本レポ : 外部へ投稿する自動処理に設定し、多重実行による重複投稿を防いでいる
 - 背景　 : 外部に副作用を出す処理は、冪等でない限り必ず多重実行対策が要る。冪等（idempotent）とは、何度実行しても結果が同じという性質

### Least privilege (workflow permissions) — 必要最小限の権限だけを与える原則

 - 本レポ : ワークフローごとに必要な権限を明示し、既定の広い権限に頼らない
 - 背景　 : 自動化は人間より速く広く動けるため、事故ったときの被害も速く広い。「読めれば足りるなら読みだけ」

### Workload Identity Federation — 長期の鍵を持たずに、CIの実行主体そのものをクラウド側に信用させる認証方式

 - 直訳　 : workload は「処理の実体」、federation は「連合」。別々の認証基盤どうしを提携させること
 - 本レポ : クラウドへのデプロイ認証に用い、サービスアカウントの鍵ファイルを保存しない構成にしている
 - 背景　 : 鍵は「漏れる」「更新を忘れる」の二重苦がある。短命な資格情報をその都度発行させるのが現代的な解。この方式には、CI側が発行するIDトークンを書き出す権限が要る

### Secret — リポジトリに置けない機密値を、実行時にだけ注入する仕組み

 - 直訳　 : 秘密
 - 本レポ : 外部サービスの認証情報や、クラウド認証の参照先をこの仕組み経由で渡す
 - 背景　 : ログにうっかり出さないことが要点。「隠されているから安全」ではなく「取り扱いを限定するから安全」

### Badge — README に埋め込む、状態を示す小さな画像

 - 直訳　 : 記章、バッジ
 - 本レポ : ビルド状態、使用技術の版、ライセンスを一目で示すために並べている
 - 背景　 : ビルド状態のバッジだけは動的に生成される実データで、他は静的な表示に過ぎない。同じ見た目でも情報の重みが違う

## 6. フロントエンド実装

### Component — UIを再利用可能な部品に切り出したもの

 - 本レポ : 共有ボタン、リンクカード、見出し、動画一覧などを部品として切り出し、記事やページから読み込む
 - 背景　 : 見た目の切り分けではなく「責務の切り分け」。同じ見た目でも用途が違うなら分ける、というのが実務的な線引き

### Props — 親から子コンポーネントへ渡す入力値

 - 直訳　 : properties（属性）の略
 - 本レポ : 共有ボタンやリンク系の部品に、表示対象や表示切替のフラグを渡している
 - 背景　 : 関数の引数と同じで、単方向。子が親の値を書き換えないことが、React の見通しの良さの根拠

### State — 時間とともに変わる、コンポーネント内部の値

 - 本レポ : メモ帳やダーツ計算機のように、操作に応じて表示が変わるページで使う
 - 背景　 : props（外から与えられ変わらない）と state（内部で変わる）の区別が最初の関門。どちらでも書ける場面では、状態は少ない方が正しい

### Client-side storage — ブラウザ内にデータを保存する仕組み

 - 本レポ : メモの内容は端末内の永続ストレージに、外部から取得した数値は短命なセッション用ストレージに保存する
 - 背景　 : localStorage はタブを閉じても残り、sessionStorage はタブを閉じると消える。「消えては困るデータ」と「キャッシュに過ぎないデータ」で置き場所を分けるのが定石

### Server-side rendering / prerendering — サーバやビルド時にHTMLを組み立ててから返すこと

 - 本レポ : ページはビルド時に描画されるため、ブラウザ専用のAPIをそのまま実行すると生成が失敗する。ブラウザでしか動かない処理は、描画後に実行されるタイミングへ寄せる
 - 背景　 : 「window is not defined」で落ちるのはこれが原因。ビルド機にはブラウザが無い、という当たり前を毎回忘れる

### Hook — 関数コンポーネントから、状態や外部の仕組みを利用するための関数

 - 直訳　 : かぎ針、引っ掛けるもの。既存の流れに自分の処理を引っ掛ける比喩
 - 本レポ : 状態管理、副作用の実行に加え、サイト設定や現在のロケールを取得する用途で使う
 - 背景　 : 呼ぶ順序と場所に規約がある（条件分岐の中で呼ばない）。これは実装都合の制約で、直感には反する

### CSS Modules — クラス名をファイル単位で自動的に一意化する仕組み

 - 本レポ : ページ固有のスタイルはモジュール形式のCSSに置き、サイト全体に効かせたいものだけ共通CSSに置く
 - 背景　 : グローバルCSSの衝突を、規約（命名ルール）ではなく仕組みで防ぐ発想。命名規則で回避するBEM等とは、同じ問題への別解

### Dark mode / color scheme — 明暗2つの配色を切り替える仕組み

 - 本レポ : 既定を暗色とし、切り替えを許可しつつ、OSの設定も尊重する
 - 背景　 : 「既定値」「利用者の選択」「OSの設定」の三者の優先順位を決めるのが設計の本体で、色を2種類作ることではない

### Accessible name (aria-label) — 視覚以外の手段で要素の意味を伝える名前

 - 直訳　 : ARIA は Accessible Rich Internet Applications の略。aria-label は「読み上げ用の名札」
 - 本レポ : アイコンだけのリンクやボタンに付与し、何のための操作かを明示している
 - 背景　 : 見た目が記号だけの要素は、支援技術にとっては無名の要素。装飾ではなく情報の欠落を埋める措置

### Client-side caching — 取得済みの結果を手元に保持し、再取得を避けること

 - 直訳　 : cache はフランス語 cacher（隠す）由来で「隠し場所・貯蔵庫」
 - 本レポ : 外部APIから取得した数値を取得時刻とともにブラウザ側へ保存し、一定時間内は再問い合わせしない
 - 背景　 : 外部サービスには利用回数の上限がある。「動くが、閲覧が増えると止まる」類の問題を先に潰す発想。保存する値に取得時刻を添えるのは、期限切れ判定をキャッシュ側だけで完結させるため

### CSV / BOM — 表形式データの平文フォーマットと、その文字コードを示す先頭バイト列

 - 直訳　 : CSV は Comma-Separated Values（カンマ区切りの値）、BOM は Byte Order Mark（バイト順の印）
 - 本レポ : 一覧データを書き出す処理で、値のエスケープを規格に沿って行い、先頭にBOMを付けて出力する
 - 背景　 : BOM を付けるのは、表計算ソフトが文字化けせず開けるようにするため。技術的には不要でも、受け取り手の都合で付ける典型例

### URL-safe encoding / compression — 文字列を圧縮し、URLに載せられる文字だけで表現すること

 - 本レポ : メモの内容を圧縮してURLに載せ、リンクとして共有できるようにしている
 - 背景　 : サーバに保存せず共有できる反面、URLの長さ制限が実質的な上限になる。「サーバを持たない」設計の代償が、そのまま制約として現れる

## 7. 公開・検索・計測

### SEO — 検索エンジンからの流入を意図して整えること

 - 直訳　 : Search Engine Optimization（検索エンジン向けの最適化）
 - 本レポ : 記事ごとの説明文を必須とし、サイトマップの出力対象を絞る等の措置を取っている
 - 背景　 : 小手先の対策ではなく「機械が読める形で正しく書く」ことが主。説明文が無いページは、検索側が本文から適当に切り出す

### Sitemap — サイト内のURL一覧を機械向けに提供するファイル

 - 本レポ : 自動生成し、タグ・著者・ページ送り・検索結果のページと日記を除外対象に指定している
 - 背景　 : 「全ページを載せるほど良い」ではない。中身の薄いページを大量に載せると、クロールされる予算が薄まる。更新日時は信号として意味があるが、更新頻度や優先度の指定はほぼ無視される

### robots.txt — クローラに対する巡回可否の指示ファイル

 - 直訳　 : ロボット（自動巡回プログラム）向けの、テキストによる案内
 - 本レポ : サイト直下に静的ファイルとして置いている
 - 背景　 : あくまで紳士協定であり、アクセス制御ではない。隠したいものはここに書くのではなく、そもそも配信しない

### Trailing slash — URL末尾のスラッシュの有無を統一する設定

 - 直訳　 : trailing は「後ろに引きずる」。末尾に付いてくるもの
 - 本レポ : 末尾スラッシュ有りに統一している
 - 背景　 : 有り無しは検索エンジンにとって別URLになり得る。どちらが正しいかではなく、統一されていることに意味がある

### Contextual search — 現在の言語や領域に絞って検索させる仕組み

 - 本レポ : 検索連携でこのモードを有効にし、日本語ページからの検索に英語ページが混ざらないようにしている
 - 背景　 : 多言語サイトで検索体験が壊れる原因の筆頭。索引を分けるのではなく、絞り込み条件として言語を渡すのが実装の要点

### Crawler / index — 巡回して収集する側と、収集結果を検索可能に整理したもの

 - 直訳　 : crawl は「這う」。網（web）の上を這い回るものが crawler。index は「索引」
 - 本レポ : 外部の検索サービスがサイトを巡回し、その索引に対して検索窓が問い合わせる
 - 背景　 : 「サイト内検索」といっても検索処理はサイト側で動いていない。だから公開直後の記事は、巡回されるまで検索に出てこない

### Analytics — 訪問状況を計測する仕組み

 - 本レポ : 計測タグを設定で組み込み、IPアドレスの匿名化を有効にしている
 - 背景　 : 匿名化は法制度上の配慮であると同時に、計測精度とのトレードオフ。何を捨てて何を測るかの選択であって、単なるオンオフではない

### Social card (OGP) — SNSでURLを共有した際に表示される画像と説明

 - 直訳　 : OGP は Open Graph Protocol（オープン・グラフ規約）。SNS間で共通の「ページの名刺」の書式
 - 本レポ : サイト共通の画像を既定として指定し、記事ごとの説明文がカードの文面になる
 - 背景　 : 一度SNS側にキャッシュされると、直しても即座には反映されない。公開前に確定させておくべき情報

## 8. セキュリティと運用

### CSP — 読み込みや通信の許可先をブラウザに宣言し、それ以外を遮断する仕組み

 - 直訳　 : Content Security Policy（コンテンツの取得に関する安全指針）
 - 本レポ : 管理画面のHTMLに指定し、スクリプト・スタイル・通信先などを種類ごとに許可している
 - 背景　 : 許可漏れは即「動かない」として現れるため、追加時は許可先の追記が要る。なお一部の指示（フレーム埋め込みの禁止など）はHTML内の指定では効かず、配信側のHTTPヘッダで返す必要がある

### Self-hosting (assets) — 外部配信のライブラリを自リポジトリに取り込んで配信すること

 - 直訳　 : 自分で（self）宿主になる（host）
 - 本レポ : 管理画面のスクリプトを外部CDN依存から自前配信へ切り替えている
 - 背景　 : 外部配信は便利だが、供給元が改竄されれば即座に自サイトの実行権限を握られる（サプライチェーン攻撃）。取り込めば許可先も減らせる

### Subresource Integrity (SRI) — 外部から読む資源のハッシュを照合し、改竄されていれば読み込まない仕組み

 - 直訳　 : subresource は「副次的な資源」、integrity は「完全性・改竄されていないこと」
 - 本レポ : 外部から読み込む数式表示用のスタイルシートに、ハッシュ値と資格情報の扱いを併記している（もう一方の外部フォント読み込みには付けていない）
 - 背景　 : 自前配信できない資源への次善策。ハッシュが一致しなければ読み込みごと失敗するため、供給元が黙って中身を差し替えても実行されない

### Pinning — 依存やベースイメージの版を固定すること

 - 直訳　 : ピンで留めること
 - 本レポ : 実行基盤のイメージ、パッケージマネージャ、脆弱性のある間接依存の版を明示的に固定している
 - 背景　 : 固定すると自動では上がらないので、更新は自分の仕事になる。「勝手に動く」と「勝手に壊れる」はコインの裏表

### Transitive dependency — 直接は入れていないが、依存の依存として入ってくるもの

 - 直訳　 : transitive は数学の「推移的」。AがBに、BがCに依存するならAはCに依存する
 - 本レポ : 脆弱性のある間接依存に対し、版を上書きして解決する指定を持つ
 - 背景　 : 直接依存より数が多く、脆弱性報告の大半はこちら側で起きる。自分では選んでいないものに責任を負わされる構造

### Least exposure (bind address) — 待ち受ける範囲を必要最小限に絞ること

 - 本レポ : 開発サーバのポートをホストのループバックにのみ割り当て、同一ネットワークの他端末からは見えないようにしている
 - 背景　 : コンテナ内部が全方位で待ち受けていても、外への割り当てを絞れば到達できない。「内側の設定」と「公開の設定」を分けて考える例

### Runbook — 運用手順を、実行できる粒度でまとめた文書

 - 直訳　 : run（実行する）+ book（帳面）。もとは工場やITオペレーションの「操作手順書」
 - 本レポ : 設定の意図や、コード外で必要な対処の参照先として言及されている
 - 背景　 : 設計文書が「なぜ」、ランブックが「どうやって」。障害時に読まれるのは常に後者

### Environment variable — 実行環境から与える設定値

 - 直訳　 : 環境（environment）に置かれた変数
 - 本レポ : 本番と開発の区別や、ビルド中のロケール判定に用いる
 - 背景　 : 設定をコードから分離する常道。ただしビルド時に評価される値と実行時に評価される値の区別を誤ると、静的サイトでは「ビルド時の値が焼き付いた」状態になる

## 9. リポジトリ運用の語

### Monorepo layout — コンテンツ・実装・インフラ定義を1つのリポジトリに同居させる構成

 - 直訳　 : mono（単一の）+ repo（repository の略）
 - 本レポ : 記事、React実装、コンテナ定義、CI定義、仕様書が同じリポジトリに入っている
 - 背景　 : 記事の修正とコード修正が同じ履歴に並ぶ利点と、変更の粒度が混ざる欠点が同居する。個人規模では前者が勝つ

### Branch strategy — どのブランチが何を意味するかの取り決め

 - 本レポ : 作業用のブランチで日常の変更を進め、公開対象のブランチへの反映が実質的なリリースになる
 - 背景　 : 「公開対象のブランチ＝現在動いているもの」という不変条件を守ることが本体。ブランチ名や数は副次的

### Conventional Commits — コミットメッセージの型を決める規約

 - 直訳　 : conventional は「慣習に従った」。奇をてらわない、の意
 - 本レポ : 種別と対象範囲を接頭辞として書く形式で統一する。CMS経由の日記コミットも、同じ形式になるよう定型文が設定されている
 - 背景　 : 機械が読めることが眼目で、履歴から自動で変更履歴を生成できる。人間にとっても、種別を先に決めると変更の粒度が自然と揃う

### Squash / merge commit — 複数のコミットをまとめるか、履歴を分岐ごと残すか

 - 直訳　 : squash は「押しつぶす」。果汁を絞るスカッシュと同語源
 - 本レポ : 統合の記録が履歴に残る形で運用されている
 - 背景　 : 潰せば読みやすく、残せば経緯が追える。どちらが正解ということはなく、後から読む人が誰かで決まる

### Dual licensing — コードと文章に別々のライセンスを適用すること

 - 直訳　 : dual は「二重の」
 - 本レポ : 実装コードは寛容な条件、記事などの内容物は継承条件付きの条件で公開している
 - 背景　 : ソフトウェア向けライセンスは文章に適さず、逆もまた然り。同じリポジトリ内で対象ごとに使い分けるのは、OSSの文書サイトでは一般的

### Generated artifact — ビルドやスクリプトが生成し、人が直接編集しない成果物

 - 直訳　 : artifact は「人工物」。考古学では「遺物」を指す語
 - 本レポ : 記事から動画情報を抽出したデータファイルが、ビルド前に自動生成される
 - 背景　 : 生成物を手で直すと、次のビルドで消える。「編集してはいけないファイル」を見分けられることが、事故防止の第一歩

## 10. 開発現場の言い回し（文化語）

この節は英語圏の開発現場で実際に飛び交う言い方を扱います。特定の実装を指す語ではないため「本レポ」はありません。

### YAGNI — 今必要でない機能は作るな、という戒め

 - 直訳　 : You Aren't Gonna Need It（あんた、それ要らないって）の頭字語
 - 背景　 : 「将来使うかも」で作った抽象は、たいてい将来の要件と合わず、しかし消しにくい。設計を怠ける口実ではなく、要件が確定してから作れという順序の話。会話では「it's YAGNI」と形容詞のように使う

### Nice to have — あれば嬉しいが、無くても成立するもの

 - 直訳　 : 持っていると良い（が、必須ではない）
 - 背景　 : must have（必須）との対比で使う。優先度の議論では、この2語に振り分けるだけで会話がかなり進む

### Good first issue — 新規参加者が最初に手を付けるのに向いた課題

 - 直訳　 : 最初の課題として良いもの
 - 背景　 : OSSでラベルとして定着した表現。「簡単」ではなく「文脈の前提知識が少なくて済む」が本義

### Bikeshedding — 本質でない些末な点にばかり議論が集まる現象

 - 直訳　 : bike shed は「自転車置き場」。原子炉の設計は誰も口を出せないのに、自転車置き場の色には全員が意見する、という寓話から
 - 背景　 : パーキンソンの凡俗法則。命名や色の議論が長引き始めたら、この語を出して切り上げるのが慣例的な使い方

### Yak shaving — 目的にたどり着くまでに、無関係な前準備が連鎖すること

 - 直訳　 : ヤク（家畜のウシ科動物）の毛を刈ること
 - 背景　 : 「Aをしたい→Bが要る→Bのためのライブラリが古い→…」と気付けばヤクの毛を刈っている、という比喩。作業報告で「まだヤクを刈っている」と言えば、進んでいないが無駄でもない状況を的確に伝えられる

### Rubber duck debugging — 誰か（何か）に説明することで、自分でバグに気付く手法

 - 直訳　 : ゴム製のアヒル人形に向かって行うデバッグ
 - 背景　 : 机上のアヒルに一行ずつ説明していると、口に出した瞬間に矛盾に気付く。人に聞く前に一度やれ、という文脈で言及される

### Bus factor — 何人が突然いなくなるとプロジェクトが止まるか、という指標

 - 直訳　 : バス係数。「バスに轢かれたら」の想定から
 - 背景　 : 個人開発ならこの値は1。属人性の議論を数値で言い表す、やや不謹慎だが定着した表現。truck factor とも言う

### Ship it — 完璧を待たずに出すこと、またはレビューでの承認の合図

 - 直訳　 : ship は「出荷する」。ソフトウェアでもそのまま「リリースする」の意で使う
 - 背景　 : 「Ship it 🚢」は承認の合図としてレビューで使われる定型句。対義的に、いつまでも出さない状態を analysis paralysis（分析麻痺）と呼ぶ

### LGTM — 見た限り問題ない、という承認の返事

 - 直訳　 : Looks Good To Me（私には良さそうに見える）
 - 背景　 : 「完全に検証した」ではなく「私の目には」と限定しているのが要点。責任の所在を曖昧にせず、しかし軽く承認するための表現

### Nit / nitpick — 些細な指摘。直さなくてもよい、と含みを持たせる前置き

 - 直訳　 : nit はシラミの卵。それを一つずつ摘まむ（pick）ほど細かい、の意
 - 背景　 : レビューで「nit: 」と接頭辞を付けると、ブロッカーではないと伝わる。指摘の重みを語彙で階層化する文化の代表例

### Blocker — それが解決しないと先に進めない障害

 - 直訳　 : 塞ぐもの
 - 背景　 : 進捗報告で「I'm blocked on X」と言えば、怠けているのではなく待ち状態だと明示できる。助けを求める最も摩擦の少ない言い方

### Strong opinions, weakly held — 主張は明確に、しかし固執しない

 - 直訳　 : 強い意見を、弱く保持する
 - 背景　 : 曖昧な意見を出して議論を長引かせるより、はっきり言って反証されたら即座に降りる方が速い、という態度。技術議論の理想形として引用される

### Happy path — 例外が何も起きない、想定どおりの経路

 - 直訳　 : 幸福な経路
 - 背景　 : 「まず happy path だけ実装する」は、手抜きではなく段階的実装の宣言。対義は sad path / error path

### Foot-gun — 使い方を誤ると自分の足を撃つような、危険な機能

 - 直訳　 : 足（foot）を撃つ銃（gun）
 - 背景　 : 「便利だが事故りやすいAPI」の評として使う。設計批判の語彙であり、利用者の不注意を責める語ではない

### Let's take this offline — この話は別途、関係者だけでやろう

 - 直訳　 : offline は「回線から離れて」。転じて「この場（会議・スレッド）の外で」
 - 背景　 : 全員の時間を使う場から、関係者だけの場へ議論を移す定型句。オンライン会議でも使われるため、直訳とのズレが大きい表現の代表

### Dogfooding — 自分たちの作ったものを、自分たちで日常的に使うこと

 - 直訳　 : eat your own dog food（自社のドッグフードを自分で食べる）から
 - 背景　 : 使っていれば不便に必ず気付く、という前提に立つ品質保証の方法論。個人サイトはこの点で理想的な環境になる

### WIP — まだ作業中で、完成していないことの明示

 - 直訳　 : Work In Progress（進行中の作業）
 - 背景　 : 未完成のまま共有して早期に方向性の合意を取るための札。付けておけば、細部を指摘されずに済む

### Rollback — 問題が起きた変更を、前の状態へ戻すこと

 - 直訳　 : 転がして（roll）戻す（back）
 - 背景　 : 「直す」より「戻す」が先、が原則。前に戻せる状態を常に保っておくこと自体が設計の一部で、不変なイメージタグを使う理由もここにある

### Post-mortem — 障害の後で、原因と再発防止を振り返る文書や会

 - 直訳　 : ラテン語で「死後」。もとは検死を指す医学用語
 - 背景　 : 人ではなく仕組みを責める（blameless post-mortem）のが現代の作法。個人開発でも、書いておくと同じ穴に二度落ちない
